# 用证据调试

先明确用户看到的失败、出现条件与预期结果。结合错误输出、代码、运行状态
和近期变化建立反馈，使它能识别原问题。例如，保存操作返回成功但重新打开
内容丢失，需要观察跨次读取，进程未崩溃不足以证明保存正常。

反馈可以从局部观察逐步收紧。按当前缺口选择探测，阅读代码、提出解释与
运行观察可以交替进行：

- 入口可驱动时，用窄测试、CLI、请求或界面动作重复症状，缩短准备过程。
- 现场不易重现而已有输入或事件记录时，回放相关部分，并说明省略的外部条件。
- 存在正常版本或配置时，对相同输入作差分，必要时二分缩小引入变化的位置。
- 故障偶发时，保留触发条件、尝试次数与发生率，改变能区分原因的条件。

判断反馈能否识别目标错误，再用它评估修复。未能复现时，按证据缺口选择
缩小条件、补充观测或分析已有记录。证据不足的解释保留为假说；已有日志、
代码或其他证据足以确定原因时，可以给出根因判断，并单独说明修复的实际
验证范围。

根据观察形成可区分的解释，说明什么观察会支持或排除它们。优先选择能区分
当前候选原因的探测，减少同时改变的变量。保留已排除原因，
避免重复无信息增益的尝试；发现共同前提不成立时重新建模。关于证据与推断
见[推理与约束](../../principles/reasoning.md)。

性能问题需要同口径的基线与测量，保留影响结果的输入和运行条件；偶发问题
一次未发生不足以证明消失。结论强度与已取得的证据相称。

在已有修复授权内处理原因，并用原始症状和受影响路径核验。选择能捕获真实
失败的回归保护；适用时在修复前确认它失败，修复后重跑原始情境。反馈只覆盖
最小复现时，还需核对缩减时省略的重要边界。若反复绕行指向设计
责任问题，按[变化与责任层](../../principles/change.md)判断修复位置和范围。

清理本次临时观测与资源，保留有用证据。交付说明原因依据、实际修复和验证；
只有诊断授权时交付结论与建议。无法取得必要环境或观测时，说明已尝试的
有效路径、限制了什么判断及继续所需条件，不把推测写成已定位根因。
