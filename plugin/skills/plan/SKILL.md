# 设计实现路径

这是人工入口，由用户主动发起；其他技能不自行启动它。负责形成可执行的工程安排；普通实现中的内部规划和计划更新不需要调用本入口。

从目标、退出条件、当前结构和关键未知出发，按需读取 [上下文约定](../../references/context.md)。没有独立 spec 不必停工：明确的用户请求也能作为依据。目标若存在影响实现的实质歧义，区分可调查的事实与需要用户决定的取舍，不擅自替换目标。

切片应形成可观察、可验证的进展。优先让早期切片穿过最不确定的关键边界：真实入口、核心逻辑、存储或外部接口中哪些组合能尽早暴露假设，就贯通哪些；不要把“曳光弹”理解成先造所有分层的空壳。需要选择探索方式时，参照 [反馈与真实路径](../../principles/feedback.md) 区分原型和曳光弹；可按问题使用 [原型能力](../prototype/SKILL.md)，并说明实验结果如何影响后续安排。

让计划回答真正影响执行的问题：切片之间的依赖、沿用哪些已有能力与设计约束、在哪里取得验证证据、如何集成，以及什么观察会触发改计划。相关依据留在需要它的切片附近，避免拆分后只剩功能清单。界面变化应安排组件状态与实际页面组合的检验；后端接通不能替代界面成立。适合并行的工作应有清楚边界和汇合点；是否使用多个 agent、多少人和怎样分工，由任务与环境决定。

涉及广泛迁移且无法一次切换时，考虑 expand-contract：先建立兼容路径，再迁移并验证使用方，最后在退出条件满足后删除旧路径。无需迁移的任务不套用该流程。验证安排参考 [共用验证约定](../../references/verification.md)，避免各切片局部通过而整体路径无人负责。

计划的粒度以能够启动下一段有价值的工作为准。简单任务在对话或现有任务记录中表达即可；只有复杂依赖、长期执行或多人协作需要时才维护独立计划。不预测所有实现细节，也不把内部工作安排变成新增产品要求。

完成时，应能据此开始工作并判断各切片何时完成，同时看清关键未知、依赖和整体退出条件。未实际验证的假设保留为假设。计划本身不扩展执行授权；用户未要求实现时，止于可审阅的安排。
