# 项目知识的职责

项目材料应让人和新会话找到当前问题需要的知识。沿用已有组织和有效约定，
有具体内容需要保存时再增加材料，不以目录齐全作为接入完成标准。

| 知识 | 维护职责 |
| --- | --- |
| Agent 入口 | 简短工作约定、相关材料与工具的发现入口 |
| 架构概览 | 当前职责、边界、依赖、数据归属与关键运行路径 |
| 领域知识 | 术语、身份、关系、合法状态和业务含义 |
| ADR | 值得长期理解的重要选择、替代方案、理由与适用条件 |
| Spec | 一次变化的目标、范围、行为和完成条件 |
| 实施计划 | 需要分步协调的工作、依赖、实际进度和恢复位置 |
| Feature map | 当前用户能力的入口、前提、操作、可观察结果与易误判之处 |
| 验证方法 | 可复用的运行、驱动、观察和清理能力 |
| 执行证据 | 某次运行的版本、条件、结果及材料位置 |

这些是职责而非必建文件。小任务可以合并相关内容；简单修复可以直接使用
任务描述与验证记录。项目没有惯例时，`AGENTS.md`、`docs/architecture.md`、
`docs/adr/`、`docs/spec/`、`docs/feature-map/` 是可用起点；领域知识较多时再
独立成文。需要同时支持 Claude 时，让 `CLAUDE.md` 引用共同入口，避免两份规则。

事实、目标和决定保持可辨。代码描述实际行为，已确认需求描述应有行为，
二者冲突需要解释。目标架构标明尚未实现；未决问题保持未决。重要决定被
替代时保留历史理由，并指明新决定。

Spec 完成后，持续需要的行为与验证知识进入 feature map；它不再承担不断
变化的现状说明。运行证据另行保存，不把某次通过写成长期正确性承诺。
索引用于定位权威材料，避免手工维护另一份执行进度。

修改行为、接口、归属或验证入口时，更新因此失真的材料。没有相关变化时
无需为交付而制造文档改动。规则的执行机制、证据和局限应能被找到，不要求
每份文档重复它们。

可移植方法留在项目，本机配置、凭据与一次性运行状态按所在环境的规则保存。
HTML 用于探索与表达，正式决定仍回到项目指定的维护位置。
