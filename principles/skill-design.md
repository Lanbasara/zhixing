# 技能设计

用于创建、修改或评价可复用的 agent 技能。知行自身也遵守这些判断。

## 写清专业承诺，保留方法选择

技能应让 agent 理解它接受什么问题、承担什么责任，以及怎样的成果算完成。
独立性依据[责任与范围](responsibility.md)，不依据流程中是否能切出一个动作。
一个技能可以包含多步推理，也可以按需调用其他能力；无需把每个内部动作都
做成入口。

完成标准应能区分履行了责任与看似完成。验证持久化需要观察保存后的真实读取，
仅有成功提示不足以证明它；研究的完成则取决于是否回答了问题、关键推断是否
有依据，以及未决事项怎样影响结论。标准随任务表达，文件、栏目或步骤齐全
不能代替成果。判断型任务可以保留未知，同时交付有依据的选择。

正文保留稳定的职责、关键判断与完成标准。具体步骤只有在顺序本身保护了
重要性质、依赖关系确实要求先后，或执行方式很难正确推断时才值得规定。
其他情况下，解释目的与取舍通常比指定路径更有用。全文可以是判断依据，
也可以按任务组合步骤与参考；形式应帮助执行者理解责任。

## 指令的价值包括它没有排除的合理路径

指导应帮助执行者作出必要判断、找到所需知识或辨认完成状态。写入前考虑：
缺少它会怎样影响成果，当前模型能否从已有职责与环境中稳定推断，以及它
引入了哪些阅读、维护和执行负担。答案不必形成固定记录，但应影响是否保留。
模型已经能稳定完成的行为可以减少重复指导；是否有增量价值，要结合实际任务
观察，不能仅凭一句话听起来正确判断。

避免把丰富的方法菜单误写成必做事项，把可用工具写成唯一实现，把用户偏好
写成普遍专业标准。提问、委派、查阅历史和跨会话恢复都应由实际需要触发。
不能因为它们有时有用，就成为所有技能的统一前置流程。

表达先让执行者知道要作出什么判断、完成什么行动。必要的限制与它所保护的
目标放在一起。沿用有清楚含义的领域概念，减少重复解释和无益同义词；概念词
与正向措辞是帮助理解的方法，其效果仍需观察，不是有保证的行为开关。

## 每种知识放在合适的维护位置

技能描述本专业行为；跨能力原则通过有意义的阅读入口共享；工具细节、领域
资料和复杂示例按需披露。项目事实、个人偏好、部署配置与个案记录留在各自
所属环境中。阅读入口、内容就近组织与环境事实的维护见
[知识与局部理解](knowledge.md)。

例子用于澄清容易混淆的判断：同样显示成功，哪种观察证明保存、哪种只证明
响应已返回。方法示例应带有适用条件，让执行者能够迁移到不同工具和对象。
保留真正有区分力的部分，不把示例扩充为需要照抄的流程或例外清单。

## 用行为评价改动，防止规则过拟合

个案暴露问题后，先按[变化与责任层](change.md)定位原因。只有需要修正规则
时才修改技能，不把所有失败都归因于“少写了一条要求”。

检验应观察技能是否改善了专业成果，以及是否保留了不同任务中的合理选择。
原失败案例可以验证针对性，条件有实质差异的案例可以揭示过拟合。判断新指导
是否值得保留时，比较原版与修改版，必要时加入没有该指导的基线；同时观察
成果与额外负担。哲学修改应通过技能维护工作检验，执行正文通过实际任务检验，
不能仅从措辞更清楚推导行为更好。方法与证据边界见
[行为检验](../evaluations/README.md)。

留意新增要求是否意外扩大范围、增加必填背景、强制固定顺序、诱发默认等待，
或使 agent 忽略已有信息。若规则冲突，重审整体表达，而不是继续叠加优先级
和例外。维护的目标是用最小自洽的指导支持丰富任务；删除失去价值的指令，
与补充必要指导同样重要。
