# 让重要承诺得到保护

识别当前设计或失误背后需要保护的性质，说明它的范围、理由与正确使用入口。
按任务区分约束设计、已有机制审查和实际落实；分析委托本身不授权修改产品。

先考虑责任归属、数据表示、接口和依赖结构能否消除错误写法，再选择类型、
静态分析、运行检查或行为验证。机制应与风险和可判定性相称，不把偏好硬化，
也不要求一条规则叠加所有保护。判断取舍见
[推理与约束](../../principles/reasoning.md)。

正确路径要真实可用。检查失败应让执行者知道违反了什么以及如何修正。
落实检查时，用符合契约的情形和历史错误或有代表性的反例，证明它能辨别
目标性质；仅有脚本或 CI 配置不等于保护已实际生效。

已有违规无法一次处理时，可以明确存量边界并阻止继续扩散，再按影响迁移。
约束不符合新需求时，连同理由、受影响调用者和验证一起修订，不能仅以删除
断言或扩大忽略范围换取通过。无法机械判定的内容保留判断依据和适用例子。

交付指出所保护的性质、选择的机制及其实际证明范围。设计、实现、验证和
交付门禁的状态保持可辨；重要取舍与执行入口归入项目现有决策材料，不另造
需要手工同步的规则账本。
