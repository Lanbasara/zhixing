# 领域与模块建模

让本次问题中的概念和关系足以支持可靠判断。复用项目已有语言与决定，
对照真实场景和代码辨别歧义；不为建模本身追求完整术语表或目录体系。

重点理解对象的身份、关系、生命周期、合法变化和状态归属。用正常路径、
边界情形与失败后的状态检验模型。相同用词可能指不同概念，相似实现也可能
承载不同知识；需要辨析时参阅[知识与局部理解](../../principles/knowledge.md)。

设计模块时从调用者要完成的事出发，明确它必须知道的事实、可依赖的承诺
与失败方式。把共同变化的知识留在清楚的责任边界内，让接口隐藏有价值的
复杂性。候选设计有真实取舍时比较不同形状，不为形式上的分层增加转发。

模型中发现的重要不变量可交给[约束能力](../zhixing-constrain/SKILL.md)
判断如何保护；不确定性适合实验时，选择能回答问题的原型或真实路径。
讨论涉及业务含义和用户承诺时，向人确认实质取舍；技术细节在已有范围内判断。

成果采用足以表达关键关系的形式：文字、调用示例、状态图或接口草图皆可。
区分现状、候选与已确认决定，保留影响后续工作的理由。按当前任务的写入
范围更新知识，遵循[项目知识约定](../../references/project-knowledge.md)，
不从一次建模自动启动正式规格或实现工作流。
