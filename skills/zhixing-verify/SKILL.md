# 验证承诺的行为

从用户期待的结果和变更的实际影响确定验证范围。使用已有验收依据与有效
证据，不把测试数量、文档齐全或某个方便入口的成功当作完成。

设计验证时，选择能够识别目标失败的初始条件、动作和观察。检查、真实运行、
回放或测量各自回答不同问题；按风险组合，避免机械叠加层次。涉及新路径或
工具缺口时，依据[共用验证约定](../../references/verification.md)建立可复用
方法，并按[项目知识约定](../../references/project-knowledge.md)维护 feature map。

执行时确认被测对象和条件，驱动相关真实入口，观察用户结果及重要副作用。
有意义的行为变化需要相应运行证据；仅测试替身、内部状态或最后一张截图，
未必覆盖实际承诺。涉及性能时，比较同口径条件并说明测量边界。

失败后区分产品问题、驱动问题和缺少前提。保留原本要证明的行为，按本次
职责处理或报告问题，不通过降低预期使结果通过。新方法实际跑通后才能作为
已证明的方法交付；未执行、受阻和不适用分别说明。

交付结论及对应版本、环境条件和证据位置，让读者看得出已证明与未证明的
范围。清理只回收本次创建且已无用途的资源，保留证据。后续变化只让受影响
的证明需要复核，不要求每次重跑全部检查。
