# 将共识写成规格

这是人工入口，由用户主动发起；其他技能不自行启动它。把已经确认的内容转成项目的正式承诺，不借文档完整性替用户补造决定或需求。

从相关讨论、现有规格和实际行为中辨认依据，缺少背景时参照 [上下文约定](../../references/context.md)。用户的明确表达不必再次确认；agent 提议、代码现状和历史设想也不自动等同于已接受需求。

规格应让实现者能够判断行为是否符合意图。按变化需要说明用户路径、范围、领域含义、可观察行为和退出条件；对容易误解的边界给出有区分力的例子。状态、身份、所有权或失败行为若会改变结果，应写清约束；不要填满与本次变化无关的章节。

验收条件应能区分成功与看似成功，避免只要求某个文件、类或测试存在。必要时使用 [验证能力](../zhixing-verify/SKILL.md) 判断如何取得证据，但不以当前实现方便与否降低产品承诺。

按 [项目知识约定](../../references/project-knowledge.md) 放置成果。稳定术语回到领域知识；需要保存理由的架构决定才进入 ADR；spec 引用这些事实，不复制成另一个维护来源。使用项目已有格式和生命周期，不附带建立新工单系统或强制审批流程。

遇到矛盾或关键未决事项，写出它影响哪些行为及退出条件。可继续正式化不受影响的部分，但不得用默认值掩盖未决、把假设标成决定，或宣称整份规格已可实现。只向用户提出确实需要其取舍的问题。

完成时，已确认的要求应有明确来源、可检验的结果和一致的术语；未决事项及其影响可见，文档状态符合实际成熟度。正式化完成不等于已授权实现，不自动启动下一人工入口。
