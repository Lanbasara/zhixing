# 建立项目协作基础

这是人工入口，由用户主动发起；其他技能不自行启动它。让下一次工作能找到可信的项目事实、执行约定与验证方法，而不是安装一套固定目录。

先理解项目已有的入口文档、代码结构、工具和实际维护方式，判断知行的相关能力怎样沿用现有入口、成果与约定。按接入需要查阅文档与实现；需要补齐背景时参照 [上下文约定](../../references/context.md)。已有材料能承担职责就沿用或整理，不另造一套知行专属真相。

向用户说明已有基础与接入判断。能从仓库查明的事实自行核对；只有尚未确定、且会影响后续协作的选择才需要讨论。已有明确约定直接沿用，不把接入变成重新决定整套开发方式。

按缺口选择要建立的内容，文档职责见 [项目知识约定](../../references/project-knowledge.md)：

- `AGENTS.md` 提供短而有效的项目入口、真实约束和条件阅读路径；使用 Claude 的项目可由 `CLAUDE.md` 引用同一份约定，避免双份维护。
- architecture 解释真实结构和依赖边界；domain 澄清影响行为的概念、身份、状态与所有权。只有已确定的事实才写成当前设计。
- ADR 保存值得长期保留的架构取舍；spec 表达待实现变化；feature-map 帮助从用户能力定位实现和证据；verification 指向可执行的验证方法。

这些是职责，不是必须创建的文件清单。保留项目已有命名和组织方式；没有可维护内容时不建空壳。出现重复真相或难以局部理解的跳转时，按 [知识与局部理解](../../principles/knowledge.md) 判断如何收敛。空项目可以记录目标和待定事项，不编造现有功能、运行命令或架构。无法从仓库确认的约束，应查明来源或显式保留未知。

建设范围以支撑当前协作为准。不要借整理文档重新设计产品、迁移工具链或改写未经授权的全局配置。发现结构问题可以说明影响与建议；仅为让目录整齐，不足以推动大规模迁移。

完成时，应能说明下一次常见任务如何找到目标、约束与验证方法，并使用相关能力继续工作。相关入口应可达，事实各有维护位置，命令与引用经过核实；实际运行验证的深度由项目条件决定，未运行的命令不得标成已验证。已有基础足够时，可以交付无需修改的接入判断；有缺口时，说明补齐了什么、还有什么影响后续工作。
